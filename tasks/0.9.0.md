# 0.9.0 — Resume Quality, Worker Diagnostics, and TUI/GUI Visibility

## Why this release exists

`0.8.3` fixed the hard failure where resumed downloads could become permanently dead.

What is still unresolved on real WAN targets:

- first resume can come back much slower than pre-pause throughput
- second pause/resume can still degrade badly in real usage
- there is not enough observability to tell whether:
  - resumed worker count rebuilt correctly
  - workers are stalled/retrying
  - the scaler is re-entering too conservatively
  - the origin/CDN is throttling resumed fresh requests

This release is about **resume quality**, not basic resume correctness.

## Current proven state

Already fixed before `0.9.0`:

- resume command is no longer lost while pause completion is still in flight
- paused-task cancel persists/stops cleanly
- workers relinquish active ranges when halted mid-stream
- a late pause cannot incorrectly snapshot a fully finished download as paused

Already validated:

- dry-run pause/resume and cancel service tests
- live local HTTP range-server single pause/resume
- live local HTTP range-server multi-connection double pause/resume

So `0.9.0` is not starting from a dead engine. It is tightening **live resumed behavior** and **visibility**.

## Core hypothesis

Pause is currently a hard transport teardown:

- active responses are abandoned
- workers are recreated on resume
- transport reuse state is lost
- scaler state is largely rebuilt from cold state

That means resumed downloads can be slower even when the control path is correct.

The likely causes are:

1. resumed transport is cold:
   - new sockets
   - new handshakes
   - fresh requests instead of reused ones
2. resumed scaler behavior is too conservative:
   - slow-start resets
   - throughput EWMA resets
   - worker history resets
3. origin throttling after repeated resumed range requests
4. no worker-level visibility in TUI/GUI

## Goals

### Goal 1 — Prove what happens after resume

After a pause/resume cycle, we should be able to answer:

- how many workers resumed
- how many are active vs stalled vs retrying
- whether scale-up happened after resume
- whether resumed requests were fresh or reused
- whether throughput collapse is from origin behavior or scheduler behavior

### Goal 2 — Improve resumed throughput quality

Resume should not always behave like a brand-new cold download.

Where safe, resumed tasks should preserve enough state to:

- rebuild concurrency faster
- avoid unnecessary slow-start penalties
- retain useful transport/scaler priors

### Goal 3 — Expose IDM-style per-connection detail

In TUI and GUI, the user should be able to inspect per-connection state in a collapsible view:

- connection id
- status: connecting / downloading / stalled / retrying / idle / finished
- current speed
- bytes transferred
- assigned range
- last request kind / retry state

Compact by default, expandable on demand.

## Phase 1 — Resume Instrumentation in `tur-rs`

Add explicit resume diagnostics to the stable event/log surface.

### Required additions

- resume lifecycle logs:
  - pause requested
  - pause acknowledged
  - snapshot stored
  - resume requested
  - resume launched
  - first resumed worker assignment
  - first resumed progress event
- task-level resumed diagnostic fields:
  - `resumed_from_snapshot: bool`
  - `resumed_worker_target`
  - `resumed_worker_active`
  - `resumed_at_ms`
- counters/metrics:
  - resumed fresh requests
  - resumed reused requests
  - resumed handshake ms
  - resumed scale adds
  - resumed scale drops

### Deliverables

- benchmark/log lines that clearly distinguish:
  - fresh download phase
  - post-resume phase
- no hidden source-diving needed to understand what the engine did

## Phase 2 — Preserve Useful Scaler State Across Resume

Investigate and carry forward safe resume priors instead of resetting everything.

### Candidates to preserve

- dominant protocol family
- reuse rate
- EWMA RTT
- EWMA handshake
- throughput EWMA or a bounded resume bootstrap estimate
- effective add threshold
- recent worker-count target

### Constraints

- do **not** blindly carry volatile/unsafe state that can poison new decisions
- any preserved state should be:
  - bounded
  - resume-only
  - easy to inspect in logs

### Deliverables

- resume bootstrap path is explicit and logged
- resumed tasks do not always re-enter with the same slow-start behavior as a fresh download

## Phase 3 — Worker-Level Runtime Diagnostics

Add a worker diagnostics surface in `tur-rs`.

### Required worker state

Per worker:

- `connection_id`
- `status`
  - connecting
  - downloading
  - stalled
  - retrying
  - waiting_for_work
  - paused
  - finished
- current speed
- bytes transferred
- current assigned range
- last retry reason class
- request protocol/version if known

### API shape

Expose this through a stable event/update structure suitable for TUI and GUI.

Do **not** make the frontend scrape logs for this.

## Phase 4 — TUI Detail View

The TUI should become the first runtime observability tool for resume behavior.

### Required TUI behavior

- task row remains compact by default
- expandable detail panel per task
- per-worker rows inside detail panel
- task-level summary fields:
  - effective active workers
  - current speed
  - ETA
  - remaining bytes
  - last scale action
  - resumed/fresh request mix

### Why TUI first

- easiest place to debug engine behavior without GUI state complexity
- good manual validation path before deeper GUI work

## Phase 5 — GUI (`tur-tauri`) Collapsible Worker View

Use the new `tur-rs` diagnostics to expose IDM-style per-connection progress.

### Required GUI behavior

- each task card has a collapsible “connections” section
- each worker row shows:
  - status
  - speed
  - progress/bytes
  - assigned range
- task card shows:
  - active connection count
  - ETA
  - remaining bytes
  - resumed state marker if the task was resumed

### Constraints

- GUI must consume real engine events
- no synthetic fake worker rows

## Phase 6 — Real WAN Validation

This phase is mandatory. Local tests are not enough.

### Required manual validation target

Primary target:

- `https://code.visualstudio.com/sha/download?build=stable&os=linux-x64`

### Required scenarios

1. Fresh download baseline:
   - record steady-state speed
2. First pause/resume:
   - wait ~30 seconds before resume
   - record:
     - resumed worker count
     - first resumed speed
     - steady resumed speed
3. Second pause/resume:
   - repeat
   - record whether worker pool rebuilds correctly
4. Cancel while active
5. Cancel while paused

### Required artifacts

- task log file
- summary note in `benchmarks/runs/`
- comparison of:
  - pre-pause vs first resumed throughput
  - first resumed vs second resumed throughput
  - worker-count rebuild behavior

---

## Non-goals

- browser challenge solving
- cookie/auth feature expansion
- unrelated GUI redesign
- HTTP/3 performance tuning beyond what resume diagnostics reveal

## Success criteria

`0.9.0` is done when:

1. pause/resume on real WAN targets is no longer a black box
2. resumed throughput degradation is either:
   - materially improved, or
   - clearly attributed to origin/CDN behavior with evidence
3. TUI shows per-worker detail
4. GUI can display collapsible per-connection progress using real engine events
5. manual VS Code URL testing is documented with logs and conclusions
